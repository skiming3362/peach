# ADR-0159：界面文字只在语言资源里，后端不写中文，日志用英文，命令行跟系统语言

- 状态：已采纳，分阶段实施
- 日期：2026-11-12
- 关系：修订 [ADR-0156](0156-interface-translation.md) 第一条（资源位置）、第三条（后端界面文案）与第七条（第三阶段批次）；需求来自 issue #398。

## 背景

ADR-0156 第三阶段已合入的①、②、③a、③b（PR #544、#600、#603、#604）给后端文字带上了 code，但中文原文仍写在 Python 里：任务名、阶段名、进度说明、显示表、报错，每一张表在 Python 里一份，在 `server.json` 里再一份，靠测试保持逐字相同。同一句话存两处，改字要改两处，测试只是在补这个结构的漏洞。

维护者要求源码里不再写死中文：界面上给人看的文字只有语言资源这一处来源；日志交给维护者排查，非中文的贡献者也要读得懂，改用英文；命令行是用户在终端里看的，跟系统语言走。

语言资源现在放在 `frontend/src/locales/`。四种发布形态（Windows、macOS、Docker、wheel）都只带 `web/`、`migrations/`、`resources/` 三个目录（`peach.bundle_resources`），后端在安装包里读不到 `frontend/src/`。

## 决策

### 一、语言资源搬到 `resources/locales/`

- 资源文件放在 `resources/locales/<语言>/<命名空间>.json`，术语表放在 `resources/locales/glossary/`。前端经构建别名导入同一份文件，后端经 `peach.interface_text` 读取，四种发布形态都随 `resources/` 一起带上。
- 资源读不到时，服务启动与 `/healthz` 明确报错，不等到某个任务跑到一半才缺键。

### 二、后端只出 code，文字由资源渲染

- 后端给人看的文字只写 code 和参数，Python 里不写中文原文，也不再维护与资源对照的中文表。
- 接口照旧在同一层下发 `message`、`error`、`progress_label` 等字段，内容在出口处由 `interface_text` 按 zh-CN 资源渲染。没更新的浏览器缓存、用户脚本和较旧的只读端读到的仍是一句完整的话。
- 库里新写入的行只存 code 和参数，读出时再渲染；`task_run` 的说明、后继结论与补全记录同此。
- Python 渲染器只支持 `{{name}}` 插值和点号嵌套。`server` 命名空间不使用复数后缀和格式选项，由测试检查。
- 后端用到的 code 必须能从代码里的登记表枚举出来（不靠扫描拼接出来的字符串），测试逐个核对中英文都有译文。

### 三、日志用英文，命令行跟系统语言

- 日志（含写进日志的异常说明）固定用英文，不随系统语言切换。日志进诊断导出与远程上报，同一件事只有一种写法，按文字和位置归并、按关键词检索才可靠。
- `peach` 命令行的输出跟系统语言：中文系统显示中文，其余显示英文；环境变量 `PEACH_LANGUAGE` 可以指定。文字放在语言资源的 `cli` 命名空间，经 `interface_text` 渲染。
- 仓库 `scripts/` 下的开发工具只给维护者与贡献者用，不进安装包。输出中英双语，跟本机语言，判据与 `peach` 命令行相同；文字在 `scripts/locales/<语言>/dev.json`，经 `interface_text.dev` 渲染，不进安装包，在 Weblate 以单独组件提供翻译。同时打印又写日志文件的一句，控制台那一行跟本机语言，写进日志的那一行用同一个键渲染成英文。复核 CSV、JSON 等产物里会被代码读回比对或写进账本的取值用英文稳定 id，读旧文件时兼容中文原值（ADR-0162，2026-11-14 修订），只给人看的说明跟本机语言。2026-11-13 修订：原定开发工具输出固定用英文；维护者希望开发工具也能用中文，并接受社区翻译。日志仍固定英文。
- 源码注释与 docstring 不在此列，仍按项目约定用中文。

### 四、内容数据不算界面文字

标签词表、汉字转换表、日文站点页面上的字段名、数据里的约定前缀（如标签的 `演员:`）是内容或数据格式，不是界面文字，按文件列入白名单留在代码里。

### 五、旧记录升级时一次性转换

已经落库或落盘的中文（任务行的说明与结论、后继的补全记录）在升级时经「修复与迁移」入口一次性转成 code，转换前备份。转换完成后，代码里不保留认旧原文的逻辑。

- 转换按模板反推：进度说明与结束原因按 zh-CN 资源认；结论段落的正式文字可以改写，转换按旧版本写进库里的措辞认，那份措辞存在 `resources/upgrade/interface-text-legacy.json`，只供转换读取，不进 Weblate。
- 改动前的原值逐条记进回执：任务行按 id，补全记录按文件名。对不上模板的（文件名、异常原文、更早版本的措辞）保留原文，界面照原文显示。

### 六、门槛

- `scripts/check_backend_copy.py` 按文件统计 `src/peach/` 源码里的中文字符串条数，上限记在 `scripts/backend-copy-baseline.json`，只减不增；统计覆盖全部字符串（含已带 code 的、日志与命令行输出），docstring 不计，内容数据文件（标签词表、汉字转换表、番号与标题规则的词表、页面原词等，登记在脚本的 `CONTENT_FILES`）整份不计。ADR-0156 时只统计路由模块里和 `raise` 报错里还没带 code 的中文，新口径更宽，首次按新口径记录时条数会上涨，这是口径变化。
- 同一个脚本按同一口径统计 `scripts/` 下开发工具的中文字符串，上限另记在 `scripts/dev-copy-baseline.json`，只减不增；整份只有数据的脚本登记在 `DEV_CONTENT_FILES`。剩下的条数是混在脚本里的内容数据，以及随源码包分发或复制到检出之外运行、读不到 `scripts/locales` 的几个脚本。`tests/test_dev_text.py` 检查中英 `dev.json` 键与占位一一对应、脚本按字面写出的键都存在、英文里的中文只是照抄的原文。`--write` 只调低上限，不调高。
- 前端「写死的中文 0 处」与全角标点检查照旧。

### 七、分阶段

| 阶段 | 内容 |
| --- | --- |
| 一 | 本 ADR；资源搬到 `resources/locales/`；`interface_text` 渲染器与启动检查；`scripts/backend-copy-baseline.json` 按第六条的新口径重记各文件的中文字符串上限。界面行为不变 |
| 二 | ADR-0156 第三阶段②、③a、③b 的 Python 中文表换成从资源渲染，删表前逐字断言渲染结果与原表相同；`UserFacingError` 与 `message_fields` 只收 code 与参数 |
| 三 | 后继结论（原③c）按本 ADR 重做；旧任务行与补全记录的一次性转换 |
| 四 | 日志改英文；`peach` 命令行输出进 `cli` 命名空间并跟系统语言；`scripts/` 开发工具改英文（量最大，可单独一批） |
| 五 | ADR-0156 原定的④～⑥（路由与领域异常、托盘与服务端 HTML、口味分析与其余）直接按本 ADR 的写法做；云下载说明与存储里的中文值（原③e、③f）随所在的域处理 |

## 不采用

- **Python 与资源各存一份中文，测试对齐**：这是本 ADR 要取消的现状，改字要改两处。
- **构建时把资源复制进 `web/dist/`**：多一份生成物，改字后要重新构建才能让后端读到。
- **接口只发 code、不发渲染好的文字**：缓存着旧前端包的浏览器和用户脚本会只剩下一串 code。

## 后果

- 改一句界面文字只改语言资源；后端测试不再核对中文表。
- Weblate 组件的文件路径随资源搬家改到 `resources/locales/`（Weblate 尚未开放，没有迁移成本）。
- 阶段二到四期间，部分模块还有中文字面量；每次抽走中文后用 `check_backend_copy.py --write` 调低这些文件的上限。

## 验证

- 安装包与 Docker 镜像里能读到 `resources/locales/`，`/healthz` 在资源缺失时报错。
- `scripts/backend-copy-baseline.json` 里各文件的中文字符串上限随每次合入下降；在内容数据文件（`CONTENT_FILES`）以外新增中文字符串（docstring 除外）的提交被 `tests/test_user_messages.py` 拒绝。
- 英文界面下任务中心、设置与报错的文字与改造前一致或更完整。
